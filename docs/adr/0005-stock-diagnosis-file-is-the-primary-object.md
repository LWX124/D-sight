# ADR-0005: 诊断档案是股票诊断的主对象

- **状态**: 已采纳
- **日期**: 2026-08-10
- **决策者**: lwx

## 背景

当前 D-sight 的股票分析能力以"聊天会话"为入口——用户在 Chat 中提问，系统触发 `deep_analysis` 后台任务，结果以消息形式返回。这种模式下：
- 历史诊断结论隐藏在对话历史中，难以追溯和比较
- 诊断结果的生命周期绑定在聊天会话上——会话删除后诊断也丢失
- 更新提醒、后验评估等长期能力缺少稳定的"锚对象"

## 决策

以 **诊断档案（`DiagnosisFile`）** 作为一等领域对象。档案长期聚合：
- 不可变诊断版本（`DiagnosisVersion[]`）
- 诊断问答会话（`DiagnosisConversation[]`）
- 更新提醒（`UpdateReminder[]`）
- 后验观察结果（`OutcomeObservation[]`）

聊天会话（Chat Thread）可以引用档案及指定版本，但不能成为诊断状态的唯一存储。
档案可以在 Chat 中创建，但一旦创建就独立于 Chat 生命周期。

## 考虑的替代方案

### 方案 A: 聊天会话即诊断状态（现状）

延长当前 `deep_analysis` 模型继续使用 Thread 存储所有诊断结果。

- **优点**: 不需要新模型，前端改动最小
- **缺点**: 版本不可追溯、提醒无法独立于聊天触发、后验数据散落在会话中
- **为什么不选**: 聊天是即时性的，诊断是长期性的。混在一起既损害聊天的灵活性也损害诊断的可靠性

### 方案 B: 诊断档案 + 强制绑定聊天

诊断档案必须关联一个 Thread，问答只能在该 Thread 中进行。

- **优点**: 问答上下文自然隔离
- **缺点**: 限制了未来的非 Chat UI（如纯档案页的独立问答区）
- **为什么不选**: 档案页内嵌问答区是更好的 UX，不应强制走 Chat 路由

## 后果

### 正面
- 诊断结果脱离聊天生命周期，可长期追溯
- 更新提醒可以独立于聊天触发（定时任务即可）
- 版本列表、后验统计等产品能力有明确的归属对象
- 权限模型简化：档案所有权 = 诊断数据所有权

### 负面
- 增加一个新的一等领域模型，需要新的 API 和前端页面
- 现有 `deep_analysis_reports` 需要迁移或适配为 `DiagnosisRun` 角色
- 用户需要理解"档案"和"聊天"是两个不同的概念（UX 设计挑战）

### 中性
- 档案和 Thread 之间是 `1:N` 关系——一个档案可以有多个关联的聊天会话（不同时间、不同角度讨论同一只股票），Thread 解绑不影响档案存在
