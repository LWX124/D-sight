# ADR-0003: 股票诊断采用不可变版本

- **状态**: 已采纳
- **日期**: 2026-08-10
- **决策者**: lwx

## 背景

股票诊断系统需要记录每次分析的结论，以便后续比较、复盘和审计。当前 `DeepAnalysisReport` 同时承担"运行任务"和"最终报告"两个角色，无法天然表达"一个诊断档案拥有多个版本的结论"。

核心矛盾：用户可能在诊断后改变持仓、更新偏好、或新数据到达后重新分析。系统需要在"保留历史结论以便比较"和"节省存储"之间做权衡。

## 决策

股票诊断的每次创建或显式更新都生成一个不可变诊断版本（`DiagnosisVersion`）。普通多轮问答（问答会话）只解释、质疑或展开指定版本，不隐式改写其结构化结论。

不可变语义：
- `DiagnosisVersion` 创建后其结构化字段不可修改。
- 需要修正或更新时，创建新版本并标记原因（`evidence_change` / `profile_change` / `method_change`）。
- `DiagnosisRun`（执行任务）是可重试的操作记录；`DiagnosisVersion` 是不可变的业务事实。两者不再混为同一 DB 行。

## 考虑的替代方案

### 方案 A: 可变版本 + 完整审计日志

每次修改记录 diff 和操作人，版本号递增。

- **优点**: 存储更紧凑，只有当前版本 + 变更日志
- **缺点**: 版本 diff 需要从日志反向计算；审计日志与业务对象一致性保证复杂；多 worker 并发写需要乐观锁
- **为什么不选**: D-sight 诊断场景版本数可控（每只股票每月 1-4 次），不可变版本带来的实现简单性超过存储成本

### 方案 B: 仅在动作变化时创建版本

只有新的 `DiagnosisAdvice.action` 与上一版本不同时才创建新版本。

- **优点**: 更少版本对象、用户只看到"有意义的"变化
- **缺点**: 无法回答"为什么上次是 Hold 而证据已经变了"——中间态缺失导致后验数据不完整；diff 的 evidence_change / method_change 追溯链断裂
- **为什么不选**: 证据变化即使没改变最终动作也是有效信号，对后验评估和校准有价值

## 后果

### 正面
- 审计简单：每个版本自包含，不需要拼接变更日志
- 缓存安全：版本 ID 作为缓存 key，不需要失效逻辑
- diff 可计算：任意两个版本之间可以精确对比
- 回放可验证：用相同 `analysis_version` 重跑 EvidencePack 应产生一致结果

### 负面
- 存储增长：每只股票每月可能产生 1-4 个版本，每版本约 50-200KB。需在 Phase 1 设计版本保留策略（如 12 个月以上版本压缩或归档）
- 需要显式版本管理：UI 需要版本时间线和切换机制

### 中性
- 问答必须绑定版本：在 Phase 3 实现时需要设计合理默认值（默认使用用户当前查看的版本）
